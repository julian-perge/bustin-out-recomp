## Decision

M0 passed. The user accepted 19 of 20 on 2026-10-10. Under the plan's literal rule it would not have passed outright, because no flag set matches all 20 functions. The best sets, `/O2 /G7 /arch:SSE` and `/Ox /G7 /arch:SSE`, match 19 of 20, and the one miss is a parked stack-slot tie.

The one miss is `0x00152660`, which writes a vector to a stream through three virtual calls. No flag set in the matrix matches it, so the cause is most likely in the source, though the matrix covers only four flag dimensions. After five attempts at its structure, the best version has the right size (117 bytes) and identical bytes up to offset 0x47. From there the compiler puts the second and third float temporaries in different dead stack slots than the original did. That is halo-1's class D (a scheduling or lifetime tie). The function is parked, and the best attempt is kept in `src/m0/fn_00152660.cpp`. That attempt declares its locals in reverse order only to get the loads in the right order, which would fail the credibility rule if it ever matched.

### How the 20 functions were chosen

All selection went through ghidra-mcp:

- Ghidra found 10,311 functions. 1,325 are unnamed, contiguous, 8 to 120 bytes long, and in `.text` with no direct calls. Indirect calls through a vtable or a register are allowed, because they need no relocation.
- 965 of those reference nothing outside their own body.
- From those, code found byte for byte in an XDK library is dropped as SDK code, along with anything in the two SDK address blocks, `0x00100143-0x0010AB90` and `0x0021DF00-0x00232C3E`. The XBE loader's symbol-database analyzer named the functions in both blocks.

The first selection had a bug: it treated any reference as disqualifying, including jump targets inside the function itself, so it excluded every function with a conditional jump. It also labeled indirect calls and tail jumps as "branches". The review caught both. The set was revised to drop eight low-information picks: three near-copies of `0x0014C7B0`, two copies of the lock idiom (`0x001224E0`, `0x00147600`), and three trivial functions (`0x00018040`, `0x001245C0`, `0x001A4990`). All eight had matched. They were replaced by eight functions of 30 bytes or more with real conditional jumps or loops, picked evenly across `.text` from 400 candidates.

### What the result establishes

- The compiler is the XDK 5558.2 `CL.Exe`, version 13.10.3077, run under wibo 1.2.0 on macOS. 19 hand-written functions compile to the original bytes, including all 8 with conditional jumps or loops.
- `/arch:SSE` is required. Without it, `0x000D20E0` stops matching: it copies three float arguments with `MOVSS`, which VC71 emits only under `/arch:SSE`.
- `/G7` is required. With `/G6` or no CPU flag, 9 more functions stop matching. That covers most of the branch and loop functions, plus `0x0004A920`, which increments a field with `ADD [mem], 1`.
- Frame-pointer omission is on. With `/Oy-`, 13 more functions stop matching. `/O1` matches at most 4 of 20.

### Still open: /O2 or /Ox

All 20 functions compile to the same bytes under `/O2` and `/Ox`. The difference is that `/O2` also turns on string pooling (`/GF`), function-level linking (`/Gy`) and stack probes (`/Gs`), none of which shows up in a single function's code.

The only evidence so far is weak. The game's `.rdata` holds 31 duplicated string values. 28 of them form two fixed-width name tables, which are arrays, so `/GF` does not affect them. Two of the rest are referenced from SDK code. The last one, `$Object`, has two copies referenced from game functions far apart (`0x000CFE30` and `0x001CD490`). `/GF` would normally merge identical literals across source files, so this pair leans toward `/Ox`. But it is one pair, and either copy could be a `char` array rather than a literal.

Project default for now: `/O2 /G7 /arch:SSE`, the usual Release setting. Keep both `/O2` and `/Ox` in the matrix until more game strings or the source-file layout in phase 3 settles it.

### Source shapes that mattered, as lessons for M1

- `0x00018790` assigns a 12-byte struct passed by value. Stores to three separate fields compile differently, because the struct copy computes the destination pointer first.
- `0x000E61A0` is `if (m_7d) return false; return true;`. The forms `!m_7d` and `m_7d == 0` compile with an extra `xor eax, eax`.
- `0x001AE610` is a virtual override of a function from a second base, reached through a virtual base. The class doing the virtual inheritance needs its own vtable. Otherwise MSVC makes the other polymorphic base primary and every offset shifts.
- `0x000F9050` copy-constructs 76-byte elements made of a vector with a user-written copy constructor plus a 4x4 float matrix. A plain struct of the same size compiles to one `rep movsd` instead of three moves plus `rep movsd`.
- `0x00085FB0` uses an array class with a length stored in front of its data, plus `Count()` and `operator[]` members. Writing the same accesses as free functions or raw pointer reads changes register choice.
- `0x001A5150` is `strcmp` between two members, expanded inline by the compiler. `0x000112D0` is the compiler's vector-constructor loop. Both matched on the first try.
