# ADR-0007: The agent workflow

- **Status:** Accepted (user decision); partly superseded by ADR-0014 and ADR-0015
- **Date:** 2026-10-11

## Context

Sessions and subagents spent time re-investigating findings that were settled or in progress. The M1 implementer rulings existed only in the gitignored subagent ledger. The setup is adapted from nv-rs (the agent-workflow design of 2026-10-11, which ADR-0014 removed).

## Decision

- `CLAUDE.md` is the entry point. `docs/STATUS.md` holds the milestone table and one Active block that each batch replaces. `docs/WORKFLOW.md` holds tool procedures.
- `docs/FINDINGS.md` is the register of facts, with a status per entry; this directory holds decisions.
- The subagent-driven-development ledger (`.superpowers/sdd/`) stays gitignored scratch. When a plan finishes, each of its rulings becomes an ADR or a finding.
- Three role agents in `.claude/agents/`: `namer` (writes to Ghidra), `matcher` and `reviewer` (read-only ghidra-mcp tools, generated by `uv run python -m bodecomp.agent_tools`). Agents propose findings in their reports; only the lead session edits FINDINGS and STATUS.
- A SessionStart hook (`tools/session-start.sh`) prints the Active block, the open and active findings, the server state and the branch at every start, resume and compaction.
- `docs/LEDGER.md` is generated from `config/symbols.txt`.

## Consequences

- A new session reads `CLAUDE.md` and the hook output, then searches FINDINGS and the ADRs before investigating.
- STATUS and FINDINGS have one writer, so parallel agents never conflict on them.
- When ghidra-mcp is updated, `bodecomp.agent_tools` must be rerun to refresh the read-only list.
