# M4 results

M4 makes matching a steady process: small functions are generated by byte shape, and larger ones go through matcher batches whose pace and token cost are tracked.

## gen_trivial

`uv run python -m bodecomp.trivial generate` recognises 13 byte shapes among game functions of 16 bytes or fewer, writes a source for each, and keeps only those that match (docs/WORKFLOW.md, "Trivial functions"). The first run kept 2246 of 2246 in 12 seconds and wrote 34 files under `src/game/trivial/`.

The README's "Functions matched" badge counts functions, so it overstates progress; the "Game code matched" badge counts bytes. ## Pace

The three batches matched 57 of 60 functions for 378,666 tokens, about 6,640 tokens per matched function: 5,893 in batch 1, 6,567 in batch 2 and 7,557 in batch 3. The rise follows the candidates, which `match candidates` takes smallest first, so each batch had larger functions than the one before; that this is the cause is a guess, since the sizes per batch were not compared. The three parked functions are a source shape the compiler would not reproduce (F-0076) and two units that hold a second `ret` no function starts (F-0078). At this rate the remaining 16,570 game functions would take on the order of 110 million tokens, and the larger functions will cost more each, so matcher batches alone do not finish the game.

The nine writable shapes cover 1,036 functions. The `ff25` row was read from the bytes as an import jump; Ghidra shows FUN_000fce00 writing the pointer, so it is game code. The vtable stores match as ordinary constructors and destructors only when the class's first virtual function is named after the address in the target vtable's first slot, so the generator has to read that slot from the xbe. No shape of the first pass fell below 90% kept, so no finding records one.

A Sonnet `reviewer` passed all nine trial sources, but it and the lead both missed what the vtable shapes stand for. Slot 0 of vtable 0x002E21BC is 0x00011220, which Ghidra disassembles as `TEST [ESP+4],1`, a store of 0x2E21BC to `[this]`, a conditional call to 0x000136E0 with `this`, and `RET 4`: VC71's scalar deleting destructor. So the real class has a virtual destructor, and a source that names slot 0 `FUN_00011220` as an ordinary virtual function is not plausible (ADR-0013). Of the 230 vtable-store functions, 189 have a slot 0 that ends in `ret 4` (a byte check; only 0x00011220 was checked in Ghidra), 18 have some other slot 0, 21 have a slot 0 at 0x0021F734 with no unit, and 2 point at 0x0035DC1C, which has no file data. The two vtable shapes are parked until `bodecomp.match` resolves the `??_E` and `??_G` names a real virtual destructor puts in the vtable (F-0080).

The second `generate` run, with the seven passing shapes, kept 3044 of 3044 functions, 798 of them new, in 16 seconds; `bodecomp.match` now reports 3122 matched. The `b8` pattern splits in two: 9 functions return a string literal, used when the text in `build/strings.tsv` encodes back to the exact bytes in the xbe, and 70 return the address of a global as `char*`. Eight of the 473 jumps were not tried, because each calls a function defined in the same 64 KiB block, and VC71 would inline that call (F-0073).

The third `generate` run added the two vtable shapes after `bodecomp.match` learned to resolve the deleting destructor a virtual destructor puts in the vtable (F-0080). With a virtual destructor, VC71 compiles the class's scalar deleting destructor `??_G` itself, and its vtable relocation names `??_E`, a weak external that stands for `??_G`. The match follows that alias, and because `??_G` has no address comment it compares the generated code's bytes and relocations with the original at the address the vtable slot expects. A trial compile showed the destructor form needs the destructor out of line and the constructor form needs it inline: with an out-of-line destructor declared but not defined in the file, `??_G` calls `??1` instead of holding the destructor's body, and does not match 0x0004A7A0. A Sonnet `reviewer` passed both shapes on 0x000111C0 and 0x0004A820, noting that the original vtables have more slots than the generated classes declare, which does not change these functions' bytes. The run kept 155 of 179 destructors and 28 of 51 constructors; the 47 others were not examined one by one, and the 41 slot-0 targets counted above as unmatchable by the byte check are the likely bulk of them (a guess). `bodecomp.match` then reported 3305 matched. Operator delete at 0x000136E0 was given the name `??3@YAXPAX@Z` with the wrong tier, `sdk` (F-0081); it is now matched from src/game/auto/000136E0.cpp, so `generate` no longer writes it, and 0x00011030, which jumps to it from the same block, is kept instead. `bodecomp.match` now reports 3306 matched.

The reviewer named three limits of the generated sources. When several `delete-this` functions of one class are matched, their placeholder virtual functions do not agree. The `jump` and `forward-member` shapes only cover calls in tail position. The `set-second-arg` and `array-count` shapes assume the member is at offset 0.

## Lessons

- A unit's bytes decide a match, not Ghidra's function size. Ghidra can end a function at an int3 inside it (F-0075), and a unit can hold a second function whose start is missing (F-0078). Both agents now say so in `.claude/agents/matcher.md` and `reviewer.md`.
- The matcher's claims about compiler behaviour need the reviewer to compile the other form: in batch 2 a claimed quirk turned out to be a different expression (F-0077). The reviewer now checks each such claim.
- A proposed finding says whether it rests on Ghidra or on bytes alone; in batch 3 the matcher read bytes only and the reviewer found that one of the two missing starts is a shared return, not a function (F-0078).
- No parked source contained steering in any batch.
